

# Подготовка лабораторного стенда для выполнения лабораторной работы

## Исходные условия

    Для выполнения задания требовалось развернуть уязвимую машину Metasploitable 2 и выполнить её сканирование с помощью Kali Linux с последующим анализом сетевого трафика в Wireshark.

    Основная сложность заключалась в том, что в качестве хостовой системы использовался MacBook на Apple Silicon (ARM64). Образ Metasploitable 2 существует только для архитектуры amd64 (x86_64), поэтому запустить его напрямую невозможно. На компьютере с процессором Intel такой проблемы не возникает.



## Создание виртуальных машин

    В VMware Fusion были созданы две виртуальные машины.

> Ubuntu Server 26.04 LTS

    Использовалась в качестве сервера Docker. Именно на ней запускался контейнер Metasploitable 2.

> Kali Linux

    Использовалась как рабочая станция. На ней устанавливались и запускались:

    * Nmap;
    * Wireshark;
    * OpenSSH Server.

    Именно с Kali выполнялось всё сетевое сканирование.


## Выбор схемы сети

    Перед началом настройки необходимо было определить, как будут взаимодействовать виртуальные машины.
    Рассматривалось три варианта.

> Bridge

    Bridge позволяет виртуальным машинам работать непосредственно в домашней сети.

    От данного варианта было решено отказаться, так как Metasploitable содержит большое количество намеренно уязвимых сервисов. В случае использования Bridge такая машина могла бы стать доступной другим устройствам домашней сети.



> NAT

    NAT обеспечивает доступ виртуальной машины в Интернет.

    Полностью отказаться от NAT нельзя, поскольку Ubuntu и Kali необходимо загружать обновления и устанавливать пакеты.

    Поэтому NAT был оставлен исключительно для выхода в Интернет.



> Host-Only

    Host-Only создаёт полностью изолированную виртуальную сеть между хостовой системой и виртуальными машинами.

    Именно этот вариант был выбран для лаборатории.

    В результате каждая виртуальная машина получила два сетевых интерфейса.

> Ubuntu

    * NAT — доступ в Интернет;
    * Host-Only — лабораторная сеть.

> Kali

    * NAT — доступ в Интернет;
    * Host-Only — лабораторная сеть.

После настройки были назначены постоянные адреса.

```
Ubuntu

192.168.209.10

Kali

192.168.209.20
```

Это позволило обращаться к виртуальным машинам по постоянным адресам независимо от того, к какой сети подключён MacBook.




## На Ubuntu был установлен Docker Engine и Docker Compose.

После установки была проверена работоспособность Docker.


## Настройка эмуляции x86_64

    Поскольку процессор Apple Silicon использует архитектуру ARM64, Docker не способен запускать контейнеры amd64 без дополнительной настройки.

    Для решения этой проблемы была установлена поддержка эмуляции процессоров x86_64.

    Сначала была проверена архитектура системы

```bash
uname -m
```

    Результат

```bash
aarch64
```

    Затем была установлена поддержка QEMU/binfmt
```bash
sudo docker run --privileged --rm tonistiigi/binfmt --install all
```

    После установки была выполнена проверка
```bash
sudo docker run --rm --platform linux/amd64 alpine uname -m
```

    Результат
```bash
x86_64
```

    Это подтвердило, что Docker способен запускать контейнеры архитектуры amd64 на ARM64 через эмуляцию.



## Загрузка Metasploitable 2

    После настройки эмуляции был загружен образ

```bash
docker pull --platform linux/amd64 tleemcjr/metasploitable2
```

    После загрузки была проверена архитектура образа
```bash
docker image inspect tleemcjr/metasploitable2 --format '{{.Architecture}} {{.Os}}'
```

    Получено
```bash
amd64 linux
```


## Выбор сети Docker

    После загрузки контейнера необходимо было определить, каким образом контейнер будет подключён к лабораторной сети.

    Рассматривались два варианта.

> macvlan

    Преимущество macvlan заключается в том, что контейнер получает собственный MAC-адрес и выглядит как отдельное физическое устройство.

    Однако для данной лаборатории этот вариант оказался менее подходящим. При использовании macvlan существуют ограничения при обмене трафиком между контейнером и родительским интерфейсом хоста. Для обхода этих ограничений обычно приходится создавать дополнительные виртуальные интерфейсы.



> ipvlan

    В итоге был выбран драйвер ipvlan в режиме L2.

    Причины выбора:

    * контейнер получает собственный IP-адрес;
    * контейнер становится полноценным участником сети Host-Only;
    * не требуется проброс портов;
        * проще настройка по сравнению с macvlan;
    * отсутствуют проблемы взаимодействия с лабораторной сетью.

    Сеть была создана командой
```bash
docker network create -d ipvlan \
  --subnet=192.168.209.0/24 \
  --gateway=192.168.209.1 \
  -o ipvlan_mode=l2 \
  -o parent=enp10s0 \
  pentest-lab
```
    Параметры означают:

    * -d ipvlan — используется драйвер IPvlan;
    * --subnet — подсеть лаборатории;
    * --gateway — шлюз сети Host-Only;
    * ipvlan_mode=l2 — работа на канальном уровне (L2);
    * parent=enp10s0 — сетевой интерфейс Ubuntu, подключённый к Host-Only;
    * pentest-lab — имя созданной сети.


## Использование Docker Compose

    Для запуска контейнера было решено использовать Docker Compose вместо команды docker run.
    Это позволяет хранить всю конфигурацию в одном файле и при необходимости запускать лабораторию одной командой.
    Был создан файл compose.yaml:

```bash
services:
  metasploitable:
    image: tleemcjr/metasploitable2:latest
    container_name: metasploitable2
    platform: linux/amd64
    privileged: true
    command: sh -c "/bin/services.sh && tail -f /dev/null"
    networks:
      pentest-lab:
        ipv4_address: 192.168.209.210
networks:
  pentest-lab:
    external: true
    name: pentest-lab
```

    В конфигурации используются следующие параметры:

    * platform: linux/amd64 — запуск контейнера через эмуляцию x86_64;
    * privileged: true — предоставление контейнеру расширенных привилегий, необходимых для корректной работы старых сервисов;
    * ipv4_address — фиксированный IP-адрес контейнера;
    * external: true — использование ранее созданной сети pentest-lab.



## Решение проблемы с запуском контейнера

    После первого запуска контейнер сразу завершал работу.
    Анализ логов показал, что внутри образа выполнялась команда
```bash
/bin/services.sh && bash
```

    После запуска всех сервисов оболочка bash завершалась, вследствие чего Docker считал работу контейнера завершённой и автоматически его останавливал.
    Для решения проблемы команда была изменена на
```bash
sh -c "/bin/services.sh && tail -f /dev/null"
```



    Такой подход позволил построить полностью изолированную лабораторию на Apple Silicon, несмотря на отсутствие нативной версии Metasploitable 2 для ARM. В дальнейшем этот стенд можно использовать не только для выполнения данной лабораторной работы, но и для других практических заданий по информационной безопасности, поскольку все основные компоненты уже настроены и готовы к работе.
